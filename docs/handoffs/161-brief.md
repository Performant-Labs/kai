# Brief: #161 source-lang-correct

Repo: Performant-Labs/kai-private (never upstream dtapps/kai). Issue: #161. Rigor: **in-session** (see "Rigor" below for why this isn't raised). UI surface: **yes** — a wireframe is required (see "UI surface determination"). Kind: two related but distinct fixes, one backend behaviour change (`internal/translate/service.go`) plus one frontend correctness/UX gap (`TranslateWindow.svelte`, `detectedLang.ts`), landing together because the issue's own comment says the second makes the first safe to ship.

Worktree: `.worktrees/0161-source-lang-correct`, branch `issue-161-source-lang-correct`, base master `096643a` (includes #84's chunking/chunk-1 identity short-circuit, #159).

## Problem

Two problems, deliberately scoped as one issue by the principal (comment on #161, filed against #11's shipped design):

**(a) A pinned source language that is wrong produces a silent no-op.** Hand-tested 2026-09-28: `default_from` pinned to `es-MX`, English text pasted and translated, comes back byte-identical to the input — no error, no warning, reads as a successful translation. Root cause: when the source is pinned (not Auto), `translateWithEngine` (`internal/translate/service.go:251`) sends the engine's request with `From: es-MX` unchanged and never asks whether the text actually is Spanish. At least Apple's engine, given a source it doesn't recognize as different, just echoes the input back rather than erroring. DeepL's own product behaviour is the model to match: when the pinned source doesn't match the pasted text, DeepL corrects the source dropdown to what it actually detects, visibly, as part of translating — the user is never left staring at an unexplained echo.

**(b) The Auto option has no stable landmark once it's relabeled.** Already shipped in #11: the Auto entry's label is replaced wholesale by `detectedSourceLabel` (`frontend/src/utils/detectedLang.ts:34`) with e.g. `"Spanish (Mexico) (detected)"` — the literal word "Auto" never appears. A user scanning the dropdown has no fixed anchor; they must already know the top entry, whose label just happens to look like a real language name plus a small suffix, is the auto-detect choice — worse once a pinned entry with the identical base name (plain "Spanish (Mexico)") sits a few rows below it. The issue's own comment says this "needs solving as part of this issue's design, not left as-is," and matters *more* once (a) ships: a user who wants to escape a bad auto-correction back to Auto needs to be able to find it.

## What the code does today (base `096643a`, read 2026-09-28)

### Backend: `internal/translate/service.go`
- `translateWithEngine` (:251) is the single per-engine seam. Same-language short-circuit first (`req.From.SameAs(req.To)` → `identityResult`, no engine call). Otherwise `callEngineChunked` runs the engine (chunked per #84 when the text is over budget), then: **only when `isAutoSource(req.From)`** (:259) does it look at `detectedSource(res, err)` and, if the detection `Covers(req.To)`, turn the whole thing into an identity result. A **pinned** source never reaches this check at all — the branch is gated on `isAutoSource`, so a pinned mismatch is invisible to this function by construction.
- `detectedSource(res, err)` (:279) is engine-agnostic: it reads `res.From` (or, on failure, `engine.DetectedSourceOf(err)`) whether or not the request was pinned. It already returns `ok=false` when there's nothing usable (an auto-echoing `res.From`, or an engine that reports its own native code baidu/youdao use, which `Covers` can't match). This is the exact primitive (a) needs — it's just never called on the pinned path today.
- `resultFrom(requested, reported)` (:389): `if !isAutoSource(requested) || isAutoSource(reported) { return requested }` — a pinned request's `From` is *always* reported back as requested, never replaced by what the engine detected. This is the qualification layer (issue #53's variant preference) and must stay true for the ordinary case; (a)'s correction has to bypass it deliberately and say so (see "Confidence-threshold decision").
- `isAutoSource(l)` (:398): `l == "" || EqualFold(l, "auto")`.
- `#84`'s `callEngineChunked` (`service_chunk.go:66`, merged today as 096643a) already runs this exact "detect on the first chunk, decide, then commit `from` for the rest of the request" pattern for **auto** sources only (:104-128): chunk 1 is sent alone, `detectedSource` is checked against `req.To` for the identity short-circuit, and separately (when it doesn't match) a recognized detection (`model.ParseLanguage`) is pinned as `from` for chunks 2..N so the source is decided once per request, never per chunk. This is the precedent to extend, not duplicate: a pinned-source correction must be decided from chunk 1 the same way, once, for the same reason (a per-chunk re-decision would let a long paste flip languages mid-translation).
- `model.TranslateResult` (`internal/model/model.go:259`) has no field for "the source was corrected" — `Identity` (:268) is the nearest precedent (`// set by the translate service only, never by an engine`).
- `model.Language` (`internal/model/model.go`): `SameAs` (:113, dialect-aware "same source/target" comparison), `Covers` (:136, detection-vs-target), `ParseLanguage` (:174, raw code → recognized code), `Base` (dialect → base alias). No confidence field exists anywhere on `TranslateResult`, and no engine reports a numeric detection confidence — OCR's `Conf float64` (`model.go:314`, `// Recognition confidence`) is a different, unrelated field on a different result type. **There is no confidence signal to threshold on beyond text length.**

### Frontend: `frontend/src/components/TranslateWindow.svelte`, `frontend/src/utils/detectedLang.ts`
- `fromLang` (:161, `$state<TranslateLang>(TRANSLATE_LANG.Auto)`) is the source select's bound value; `TRANSLATE_LANG.Auto` is the literal auto code.
- `detectedFrom` (:536, `$derived`) reads `activeResult?.from` — whatever the backend reported for the currently-displayed engine's result.
- `fromOptionLabel(value)` (:537-546) calls `detectedSourceLabel(value, TRANSLATE_LANG.Auto, detectedFrom, langName, t('translate.detected'))`; falls back to `langName(value)` when it returns `null`.
- `detectedSourceLabel` (`detectedLang.ts:23-34`): returns `null` unless `fromLang === autoCode`; returns `null` if nothing detected (`detectedFrom === '' || detectedFrom === autoCode`); otherwise returns `nameOf(detectedFrom) + suffix` — a **full replacement** of the option's text, e.g. `"Spanish (Mexico) (detected)"`. This is exactly what #11's own follow-up comment flags: nothing in that string says "Auto".
- The option list itself (:899-901, source select): `{#each languages as l}<option value={l.value}>{fromOptionLabel(l.value)}</option>{/each}`. `languages` (:160, loaded by `loadLanguages()`/`GetLanguages`) is the full list including the Auto entry (`TRANSLATE_LANG.Auto` is one of its values, per `GetLanguages`/`fallbackLanguages` at :717-722 which maps `ALL_TRANSLATE_LANGS`, and `ALL_TRANSLATE_LANGS` includes Auto — confirmed by `langName(value)` being called for it in the fallback branch same as every other entry). So the Auto option is rendered by the exact same `<option>` templated with `fromOptionLabel`, which is the single relabeling chokepoint — no separate "Auto row" markup exists to redesign around; the fix is entirely in what `fromOptionLabel`/`detectedSourceLabel` return for the Auto value.
- `onLangPicked(ev)` (:706-709): fired **only** by the two selects' own `onchange` (:896, :932). Calls `learnLangVariant(value)` (→ `learnFromSelection` → the backend's `LearnLangVariant`/`langpref.Store`, issue #53) then `persistLangs()` (writes `default_from`/`default_to` to the settings file). `swap()` (:768-777) and `loadDefaults()` (:679-687) assign `fromLang`/`toLang` directly and deliberately never call `onLangPicked` — the existing, load-bearing rule is "assigning the state directly never teaches; only the select's own user-driven `onchange` teaches." This is precisely the rule (b)'s auto-correction must also follow: the correction must assign `fromLang` (and whatever pinned entry is affected) directly, never route through `onLangPicked`/`learnLangVariant`/`persistLangs`.
- The toast mechanism already exists and is reused, not invented, across two windows: `TranslateWindow.svelte:842-847` — `let toast = $state('')`, `showToast(msg)` sets it and clears it after a fixed 1.6s timer (`toastTimer`), rendered at :1363-1364 as `{#if toast}<div class="u-toast">{toast}</div>{/if}`. Used today only by `copy()` with `t('common.copied')` (:854). `ScreenshotWindow.svelte` has an identical independent copy (:238-244, 638-642) — the two windows do not share a component, but the pattern (state string + timer + `u-toast` div) is identical and this issue's toast belongs in `TranslateWindow.svelte`'s own copy, the same as #145 (below) added the cancel toast to it.
- `#53`'s variant-learning path (`learnLangVariant`/`persistLangs`) is the mechanism (a) must NOT feed: an engine-detected correction is not a user's deliberate pick, and teaching it back would let one auto-corrected guess silently become the new default pin for every future translation — the opposite of what a correction should do.

## Acceptance criteria

### (a) Auto-correct a pinned source language that doesn't match the actual text

1. When the source is pinned (not Auto) and the request's text is long enough and confidently-enough detected as a **different** recognized language than the pin (see "Confidence-threshold decision"), the request proceeds with the **detected** language as the effective source, not the pin: the engine's translation is the one the corrected source produces (not the identity echo the wrong pin causes today), and the result reports the corrected `From`.
2. The correction is decided once per request, from the first chunk only (mirrors #84's existing auto-source pattern in `callEngineChunked`, :104-128) — never re-decided chunk to chunk.
3. The correction never happens silently: the result the frontend receives says a correction occurred (a new boolean, see "Reuse map" / `model.TranslateResult`), and the frontend shows a visible cue when it fires (see "Visible-cue mechanism"). A translation that used the pin as given (no correction) shows no cue, same as today.
4. An engine that reports no usable detection on the pinned path (many engines simply translate as instructed and don't echo a distinguishing `From` when given an explicit source; baidu/youdao's native-code detections that `Covers` can't match) makes no correction — this is an accepted, stated limitation (see "Scope limits"), not a bug: (a) reuses whatever detection an engine already surfaces through the existing `detectedSource`/`engine.WithDetectedSource` plumbing, and does not add a second detection call to engines that don't report one on a pinned request.
5. A correction to a language the target select can't hold, or to the same language as the target (`SameAs`/`Covers` territory) is decided by the same identity-result rule already in `translateWithEngine` — no new same-language branch.
6. The corrected source is **not** taught back to the variant-preference store (`learnLangVariant`/`persistLangs`) and does **not** overwrite the user's saved `default_from` pin. The next translation (of different text) still starts from the user's original pin. This is a per-request override, not a re-pin.
7. `TranslateMulti` (parallel fan-out, `internal/translate/service.go:432`) and the single-engine `Translate` path both go through `translateWithEngine`, so both get the correction for free — no separate wiring per caller. The screenshot flow (`ScreenshotTranslate`) always sends `from := model.Auto` (:790) and is untouched by (a) (a pinned mismatch cannot occur there today).

### (b) Auto landmark redesign

1. The Auto entry in the source dropdown always visibly contains the word "Auto" (or the i18n equivalent), in every state: no result yet, a result with a detection, a result with no detection, and — new with (a) — after a pinned entry elsewhere in the list was just auto-corrected.
2. A concrete pinned language's own entry (e.g. plain "Spanish (Mexico)") is never relabeled or suffixed by the detection feedback; only the Auto entry carries the "(detected: …)" information. (Unchanged from #11 — stated explicitly because (a) makes it load-bearing: the user must be able to tell "my pin was silently corrected this once" apart from "I am looking at the fixed Auto entry.")
3. The redesigned label is the single relabeling chokepoint (`detectedSourceLabel`/`fromOptionLabel`) — no second markup path for the Auto `<option>`.

## Confidence-threshold decision (concrete rule)

There is **no per-detection numeric confidence available from any engine** for translation (grepped `internal/model`, `internal/engine`: nothing beyond OCR's unrelated `Conf` field on `model.OcrResult`). The rule the issue asks for ("minimum text length + minimum detection confidence if the engine reports one") therefore reduces, honestly, to a **length gate alone**, stated as such rather than implying a confidence signal that doesn't exist:

- **Rule: a correction only fires when the request's trimmed text is at least 20 Unicode code points long**, citing #119/#151's epic context directly: "Apple's own guidance covers only the short end (language-detection reliability under ~20 characters)" (#151 epic body) — the same ~20-character floor `internal/engine/input_budget.go:124`'s comment already references for a different reason (youdao's signature input is cut to 20 characters). Below the floor, the pin is honored as given, exactly as today (no correction, no cue) — a short fragment ("ok", "sí", a name) is exactly the case where a detector is least trustworthy and a wrong "correction" would be worse than today's silent echo.
- **The gate is on the whole request's text, not per-chunk**: for a chunked request (#84), the 20-code-point check is against the full `req.Text` before the chunk-1 detection is even attempted — mirrors the existing chunk-1-decides-for-the-request shape, and avoids a large paste whose *first* chunk happens to be short skipping the correction it should get.
- **The detection itself still has to be "confident" in the one sense available**: `detectedSource`'s existing `ok` return already excludes an engine echoing the auto code back and an unrecognized native code (baidu/youdao) — i.e., the existing plumbing already discards the low-signal cases it can detect. No new confidence math is invented on top of that; the 20-character floor is the whole of the "confidence threshold."
- This is a decided rule, not left open for T/F to invent independently — the wireframe (below) does not need to re-litigate the number, only show the cue's behavior at/around it if useful for principal sign-off.

## Auto-correction must not get taught back into `learnLangVariant`/`persistLangs`

Concretely: the correction must be applied entirely within the backend request/response for that one translation and, on the frontend, must update only the **displayed** state (`fromLang` for that window, so the dropdown reads correctly and the swap button's `swapPair` computation stays consistent) via **direct assignment**, exactly the way `swap()` (:772-773) and `loadDefaults()` (:682-683) already assign `fromLang`/`toLang` without going through `onLangPicked`. It must call neither `learnLangVariant`/`learnFromSelection`/`LearnLangVariant` (the backend `langpref.Store`) nor `persistLangs` (which would silently overwrite the user's `default_from` in the settings file). This is the same "assign directly never teaches" contract #145 already relies on and that `swapWindow.test.ts:49` already contract-tests for `swap()` (`expect(swap()).not.toContain('learnFromSelection')`) — the new correction path gets an equivalent contract test (see "Tests to author").

Backend-side, `resultFrom` (:389) must **not** be the thing that performs the correction: it is the #53 qualification layer for auto results and must keep returning the pin unchanged for an ordinary pinned request (its existing `if !isAutoSource(requested) ... return requested` branch stays exactly as it is for every request this correction doesn't touch). The correction is a **request-shape change** decided before the engine call commits (in the same place #84's chunk-1 decides `from` for the rest of a chunked pinned/auto request) — the corrected language becomes the *effective* `From` the engine is asked with and the result reports, while the flag that says "this was corrected" is what tells the frontend (and, transitively, keeps `resultFrom`/`persistLangs`/`learnLangVariant` out of the loop) not to treat it as a user pin.

## Visible-cue mechanism

Reuse the existing toast (`TranslateWindow.svelte:842-847`, `showToast`/`toast`/`u-toast`, the same mechanism #145 wired the cancel toast through and `copy()` already uses for `t('common.copied')`). No new toast component, no new UI chrome:

- When a result with the new "corrected" flag arrives for the active engine, call `showToast(...)` with a new i18n string naming what happened, e.g. `t('translate.sourceCorrected', { lang: langName(correctedFrom) })` → "Source corrected to Spanish (Mexico)" / zh-CN equivalent. New key, not a reuse of `translate.detected` (that string is the dropdown-label suffix, not a sentence).
- The toast fires once per corrected result, keyed off the same result-arrival path the `EventTranslateResult` handler already has (:585-597) — not from `doTranslate()` itself (which doesn't yet know if the backend will correct anything).
- The dropdown itself should also visibly reflect the correction for the rest of that session's display — this is a UI surface decision the wireframe settles (does `fromLang` get reassigned to the corrected language so the pinned dropdown now shows the corrected entry selected, with the toast as the one-time announcement of *why* it changed? or does the dropdown stay showing the original pin with only the toast and a cue on the result pane? — recommendation: reassign `fromLang` directly, the same way `swap()` does, so the dropdown and the actual request are never in disagreement; the toast is what explains the jump). State this as a wireframe decision, not pre-decided here, because it's genuinely a visual/interaction call the way #145's D2 (which requests keep the previous result) was.

## Auto-landmark redesign (concrete proposal)

**Proposal: `detectedSourceLabel` keeps "Auto" as a fixed prefix and appends the detected-language feedback as a distinct clause, never replacing it outright.**

Concretely, change `detectedSourceLabel`'s Auto-row return from `nameOf(detectedFrom) + suffix` (today: `"Spanish (Mexico) (detected)"`, replacing "Auto" entirely) to something of the shape `t('translate.autoDetected', { lang: nameOf(detectedFrom) })` → **"Auto — detected: Spanish (Mexico)"** / zh-CN "自动检测 — 已识别：西班牙语（墨西哥）" (i18n picks exact punctuation/wording; the shape — literal "Auto" word, an em dash or similar separator, then the detected name — is the decision). This is chosen over the alternatives considered:

- *An icon/prefix instead of text* — rejected: adds a new visual affordance (icon asset, tooltip) to a plain-text `<option>` list, where every other entry in the same list is plain text; inconsistent and a bigger UI-surface footprint for no comparability gain.
- *A separate, permanently-visible "Auto" row plus a second, separate "detected: X" row* — rejected: doubles the list length by one entry conditionally, which is more disruptive to a `<select>`'s option ordering/scanning than fixing the text of the existing row, and the issue comment's own suggested wording ("Auto (detected: Spanish (Mexico))") is explicitly a single-line fix, not a second row.
- *Keep "Auto" first, put the detected feedback in a disabled/greyed helper option right under it* — rejected for the same reason: `<option>` elements can't render two-line or styled sub-text cheaply cross-platform (WKWebView on macOS), and it's more UI surface than the one-line rewrite needs.

This changes only `detectedSourceLabel`'s return value and the new i18n key it uses (`translate.autoDetected` replacing the bare use of `translate.detected` for that one call site; `translate.detected` itself stays for any other use — check no other call site exists before removing it, likely none does per the earlier grep, so leave the key even if newly-unused rather than risk removing something `keys.test.ts`'s catalog check still needs elsewhere). `fromOptionLabel` and the `<option>` template (:899-901) are otherwise untouched — this is the single chokepoint the issue itself points at ("I only found it by reading `TranslateWindow.svelte`'s source").

## UI surface determination

**This needs a wireframe. Say so explicitly, and require it before T** — this is not a case where the existing rendering already covers it (unlike, say, a pure backend bugfix). Two genuinely new visual states are being introduced to a window the principal actively hand-tests (per #145's precedent on this exact file) and per the issue itself flagging a usability defect from direct use, not from a test: the corrected-source toast text and how the dropdown reflects a correction (the open question flagged above), and the redesigned Auto-row label in the four states (no result / detected via Auto / detected via a correction / a plain pinned entry for comparison). Both interact with existing chrome (the toast stack, if a "Copied" or "Cancelled" toast could double-fire — the wireframe should show they don't overlap) and both are exactly the kind of "does this read right in the actual dropdown/toast at real widths, light and dark, both locales" call #145's wireframe existed to settle for this same file.

**Wireframe requirements** (`docs/handoffs/161/wireframe.html`, low-fi HTML, light+dark, en-US+zh-CN, zoom control 150% start with `-`/`+`/`0` keys — same convention as `docs/handoffs/118/wireframe.html` and `145/wireframe.html`), to draw:

1. The source dropdown open, showing all four label states side by side: Auto with nothing detected yet (bare "Auto"), Auto with a detection ("Auto — detected: Spanish (Mexico)"), a plain pinned entry unaffected ("Spanish (Mexico)"), and — the new state — a pinned entry that was just auto-corrected (whatever the dropdown reads immediately after a correction, per the open question above: either the corrected language now selected, or the original pin still shown; the wireframe is where the principal picks).
2. The source-corrected toast, positioned next to the existing "Copied" toast for comparison (same `u-toast` styling, same convention #145's wireframe used for its cancel toast vs. copied toast), both themes, both locales, with a realistic language name filled in.
3. The two toasts never shown stacked/overlapping in the same interaction — the wireframe should show or state (a caption is fine) that a correction firing does not race a "Copied" click in a way that garbles either one, given the shared `toast` state (only one can be visible at a time by construction — the wireframe just needs to make that legible, not invent new stacking behavior).

## Scope limits (explicit)

- **No change to which engines are enabled** or to engine registration/config (`internal/engine`, `internal/configstore`).
- **No change to #84's chunker** (`chunk.go`, `Split`, `chunkTarget`) — this reuses `callEngineChunked`'s existing chunk-1 decision point, it does not touch chunk sizing or the reassembly (`join`/`sepAfter`).
- **No change to the request registry** (#109, `requests.go`/`activeRequest`/`engineRun`) — a correction is decided synchronously inside one engine's existing call path, not a new kind of request or a new cancel surface.
- **No second/parallel detection call.** An engine that doesn't surface a usable `From` on a pinned request (per `detectedSource`'s existing `ok` semantics) gets no correction — accepted limitation, not a follow-up TODO to silently work around later with a dedicated "detect" engine call.
- **No numeric confidence.** The 20-code-point floor is the entire threshold; do not invent a confidence score or heuristic beyond it.
- **The screenshot window is untouched.** `ScreenshotTranslate` always sends `from = model.Auto` (:790); a pinned mismatch cannot occur there. `ScreenshotRetranslate` accepts an explicit `from`/`to` (:865) and in principle *could* hit this same bug, but it is out of scope here — flag it as a candidate follow-up issue only if F notices the shared code path makes it trivial to also cover; do not go looking for it.
- **No change to `learnLangVariant`/`langpref.Store`/`persistLangs` themselves** — the correction must route around them, not modify their contracts.
- **No change to the swap button's logic** (`swap()`, `swapLanguages`) beyond whatever direct-assignment convention it already demonstrates being followed by the correction handler; `swapPair`'s derivation is untouched.

## Tests to author (T, before F writes code — in-session pipeline, no dual-review gate)

Backend (Go, `internal/translate`):
- A pinned request whose text (≥20 code points) is confidently a different recognized language than the pin: result reports the corrected `From`, `Corrected: true`, and a real translation (not an identity echo of the mismatched pin) — using the existing fake-engine test seam this package already has for `translateWithEngine`/`callEngineChunked` (real HTTP loopback fixtures per this repo's no-mocks convention, matching #11's own T (a): "engine populates `From` from a loopback `httptest.Server` fixture via its `Endpoint` config").
- Same text under 20 code points: no correction, pin honored as given, `Corrected` false/absent — the existing silent-echo behavior for a too-short mismatch is intentionally unchanged.
- A pinned request where the engine's reported `From` is unrecognized (baidu/youdao-style native code) or is the auto code echoed back: no correction (`detectedSource`'s existing `ok=false` path covers this; confirm it's exercised on the pinned branch, not just the auto branch it's tested on today).
- A pinned request where the detected language equals the target (or `SameAs`/`Covers` the pin already, i.e. no real mismatch): unchanged behavior, no spurious correction, no identity-result mislabeling.
